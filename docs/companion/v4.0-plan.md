# v4.0 plan: the app students download

Written on 28 Nov 2026 for the agent that will build it. Jiven Chana owns every decision in it. Read `CLAUDE.md`, `AGENTS.md` and `docs/companion/SDLC.md` first: they apply to all of this.

**Status: approved by Jiven on 28 Nov 2026. Section 9 lists seven things that are still his to answer: ask each when its part is reached, and do not build past an open question.**

## 1. What v4.0 is

Up to v3.2, LockedIn runs only from a developer's checkout (`npm run dev`). v4.0 makes it something a student installs:

1. **Part 1.** Four faults a new user meets on a fresh install are fixed.
2. **Part 2.** LockedIn is packaged as a desktop app for macOS (Apple Silicon and Intel), Windows and Linux.
3. **Part 3.** The app works with no settings file: the phone relay's address is built in, and dictation works without the user's own key.
4. **Part 4.** A release pipeline builds the installers, and installed apps find updates.
5. **Part 5.** A website offers the download.

Base: `main` at tag `lockedin-v3.2`. Nothing changes on the phone app except what Part 3 adds to the relay.

## 2. What exists already (read on 28 Nov, at v3.2)

LockedIn is a fork of LearnHarness 0.6.1, which ships as a desktop app. Most of the machinery is in this repository, still set up for the upstream product.

| Piece | Where | State |

| Packaging | `electron-builder.yml`, `scripts/build-server.mjs`, `scripts/after-pack.cjs`, `npm run desktop:dist` | macOS arm64 (DMG and ZIP), Windows x64 (NSIS), Linux x64 (AppImage and deb). App id, name, icons, the microphone text and the update feed are upstream's. `desktop:dist` has upstream's Apple team id baked in |

| Release pipeline | `docs/desktop-release.md`, `scripts/verify-release.ts`, `tests/verify-release.test.ts` | The guide and the checker are here. **What decision 3 costs, so nobody is surprised.** A Mac app that Apple has not notarised is blocked on first open: the user goes to System Settings, Privacy & Security, "Open Anyway". Electron's updater does not install updates on an unsigned Mac app, so Macs are told a new version exists and sent to the website. Windows shows "Windows protected your PC" once at install; its updates work. Linux is unaffected.

## 5. Part 1: four faults on a fresh install

Each was reproduced on a copy of Jiven's own trial data (a fresh setup with 14 uploaded files).

### 5.1 Weeks

**Was:** a unit has one week, or since v3.1.1 a range (`week`, `weekTo`), set from a control on each unit that lists 20 weeks. The 20 is a constant in `set-week.tsx`, `material-upload.tsx`, `screens/welcome.tsx` and `screens/library.tsx`. A whole-module PDF leaves every unit with no week (his trial: 10 Game Theory chapters and 5 RAC units).

**Build:**
- A unit holds a set of weeks: `weeks: number[]`, sorted, no repeats, possibly not adjacent. `week` stays as the first of them, for ordering. A stored `weekTo` is read as its range and not written again.
- "Set weeks" is one sheet per module: a row for each unit made from material, a column for each teaching week, a tick box in each cell. Several weeks for one unit and several units in one week are both just ticks. This week's column is marked. One Save.
- The columns are the term's weeks, from the same rule Progress uses (`termFor` in `score.ts`: the timetable's term, or 12 weeks with no timetable). Never 20. **Proposed, to confirm (9.1):** if a unit already has a week beyond the term, the columns run that far; a "one more week" control adds a column, up to 52.
- The sheet opens from a module's header in the Library, and by itself straight after an upload that leaves any unit with no week (setup step 3 and "Add course material").
- The per-unit control goes. A unit's row shows its weeks as text ("Weeks 2, 3" or "Week not set") and opens the sheet.
- Everything that asks "is this unit in week n" uses the set (`coversWeek`): this week in Learn, the Library's grouping, the week plan.
- Timetabled lectures keep the week the calendar gives them and are not rows.

### 5.2 Concept map

**Was:** `.li-idea[data-s="notyet"]` is transparent, dashed and has no shadow. On a fresh install every idea is "Not yet", so the map is a page of dashed outlines.

**Build:** "Not yet" is a solid block: card fill, solid outline, the hard shadow, with its "Not yet" tag. Colour means progress only (mint secured, the mint bar getting there, lilac to revisit). The legend's "Not yet" chip loses its dashes too. Check a fresh map and a map with all four states, light and dark.

### 5.3 Slides tab

**Was:** a lecture page's Slides tab is one collapsible row per page (`SlideRow` in `screens/lecture.tsx`): 120 rows for his deck.

**Build:** a viewer. One page large (`SlidePage`, as Learn's Slide panel uses), Previous and Next, the arrow keys, and a "go to page" box. Beside it, the lecture's ideas in map order, each with its pages, as jump links; the idea whose pages hold the current page is marked. On a narrow window the ideas sit above the page. A slide link anywhere on the lecture page opens this viewer at that page. No list of every page.

### 5.4 End of setup

**Was:** one large "Learn: <title>" for a unit `setupEnd()` picks, and a small "Go to Today". Several units can share a title, so the user cannot tell which one is meant.

**Build:** "What would you like to do first?" with three equal choices:
- the suggested unit, named with its module and week, and one line saying why it is suggested;
- "Pick something else": the units that have material, grouped by module, each with its weeks; choosing one starts Learn on it;
- "Not now": go to Today.

Nothing starts until one is chosen.

**Seen in the same trial, not decided:** units made from one file a week all take the module's name ("Neural Computation" six times, "3RC Computation" five times). See 9.2.

## 6. Part 2: the desktop app

### 6.1 First, a rehearsal build (before any other Part 2 work)

On a Mac, make an unsigned LockedIn build from `main` with the smallest changes that let it start, install it on a clean user account, and write down what happens for each of these. The answers decide the rest of Part 2.

1. Does the app start, and does `/` reach LockedIn's app at `/app`?
2. Are LockedIn's prompts and seed in the payload (`companion/prompts`, `companion/seed`)? `default.ts` reads them from `PATHS.root`.
3. Does first-run setup complete on real files: timetable, upload, study packs, the week?
4. Does "Connect ChatGPT" work from LockedIn's Me screen inside Electron? The engine's desktop sign-in runs in the main process (`electron/chatgpt.cjs`); LockedIn's screen has only been used in a browser.
5. Where do the window buttons fall on LockedIn's top bar, on the Learn screen's bar and on the setup screen? Can the window be dragged?
6. Does a downloaded copy open? Put the DMG on a web server, download it with a browser, and follow "Open Anyway". On Apple Silicon an app with no signature at all is reported as damaged, so the build must at least be ad-hoc signed: confirm the `electron-builder` setting that does this in version 26 and that the result opens.
7. Does the microphone prompt appear and does dictation run?

Report the findings to Jiven before continuing. Anything that fails becomes a task here.

### 6.2 Identity

- App name "LockedIn"; `PRODUCT_NAME` in `main.cjs`, so the data folder is `LockedIn` (and `LockedIn-dev` in development). Proposed app id `com.lockedin.companion` (9.3).
- `electron-builder.yml`: product name, app id, artifact names, the microphone sentence, Linux desktop name.
- Icons from LockedIn's mark (the four blocks in `Logo`, `components/lockedin/icons.tsx`): `build/icon.icns`, `icon.ico`, `icon.png` through `scripts/make-icons.mjs`. Upstream's layered macOS icon (`build/icon.icon`) needs Xcode 26 and is dropped unless Jiven wants one.
- `package.json` version becomes `4.0.0`. Desktop releases are tagged `v4.0.0`: `SDLC.md` reserved `v` tags for exactly this tooling.

### 6.3 Targets and signing

| System | Build on | Package | Signing |
|---|---|---|---|
| macOS Apple Silicon | an arm64 macOS runner | DMG | Ad-hoc only; not notarised |
| macOS Intel | an Intel macOS runner (confirm the label GitHub offers) | DMG | Ad-hoc only; not notarised |
| Windows x64 | `windows-2025` | NSIS installer, per user | None (as upstream) |
| Linux x64 | `ubuntu-24.04` | AppImage | None |

Each is built on its own system: Next traces native binaries for the machine it builds on (`docs/desktop-release.md`). `notarize` is off, the `.deb` target and the macOS ZIP target go (the ZIP exists only for the updater that unsigned Macs cannot use). Signing stays a switch: the plan must not make it harder to turn on later.

### 6.4 LockedIn's screens inside the window

- The root knows when it is in the desktop app and on which system (`window.lh` is present), and marks itself.
- The top bar, Learn's bar and the setup header are drag regions; every control in them is not.
- macOS: room at the left for the three window buttons. Windows and Linux: room at the right for the native buttons, from `env(titlebar-area-*)` as the engine's pages do. "Now" and the date must not sit under them.
- Links that leave the app open in the browser (the shell already does this); check LockedIn's (source, privacy, the phone link).
- All of 6.4 at every window size in section 4, on each system.

### 6.5 What must not ship

The packaged app has no facilitator routes (`COMPANION_DEMO` unset), no `runs/`, no test data, no keys. Extend `tests/desktop-payload.test.ts` for anything Part 3 adds.

## 7. Part 3: working with no settings file

### 7.1 The relay's address

The production relay's address is a constant in `policy.ts`. `COMPANION_RELAY_URL` still overrides it (development, tests). With neither, the laptop works alone as now. Tests never reach the real relay.

Installed copies will be on different versions at once, so from v4.0 the relay must keep answering older apps: no change to an existing route's meaning, only additions. Write that rule into `relay/README.md` and `docs/companion/API.md`.

### 7.2 Dictation without a key

- A new relay route hands out a short-lived Deepgram token. The key is a Worker secret that Jiven sets himself (`wrangler secret put`); it is never in the repository, the app or a chat.
- Each installed copy has a random id, made once and kept with its data, sent only to this route. It is not linked to anything else.
- Caps, in `policy.ts` on the relay's side. **Proposed, to confirm (9.4):** 60 tokens a day for one copy; 5,000 a month across all copies. Past a cap the route says so and the Speak button reads "Dictation is busy. Try later, or add your own key in Me."
- The laptop asks for a token in this order: its own key if the user saved one, else the relay. `ai.status().voice` is true when either can answer.
- A token only starts a recording; it does not limit how long it runs. So the app stops a recording after two minutes (proposed, 9.4), and the real ceiling on cost is the Deepgram account itself: Jiven should keep it on prepaid credit with no automatic top-up, if Deepgram allows that (to confirm in his console).
- `app/api/stt/token/route.ts` is an engine file: the smallest change, listed in `NOTICE`.
- The website and Me say plainly that speech goes to Deepgram when Speak is used.

## 8. Parts 4 and 5: releases, updates, the website

### 8.1 The pipeline

Bring back `release.yml` from upstream (the commit in section 2) and change it for LockedIn:

- **Manual run:** builds all four installers and keeps them as workflow artefacts for a week. Publishes nothing. This is the rehearsal.
- **A `v<version>` tag that matches `package.json`:** the gates, then four packaging jobs upload to one **draft** GitHub release on `Jiven-Chana/lockedin-companion`, then `scripts/verify-release.ts` checks the draft. The workflow never publishes.
- `verify-release.ts` and its test are changed for the new set of files: two DMGs, the Windows installer and its blockmap, the AppImage, and the feeds `latest.yml` and `latest-linux.yml`. No macOS feed.
- No signing secrets. `GITHUB_TOKEN` is enough.
- CI gains the engine's native checks on macOS and Windows if they are cheap enough to keep (upstream had them; they were removed with the workflows).

### 8.2 How an installed app updates

| System | What happens |
|---|---|
| Windows, Linux | As the engine does: checks at start and every 24 hours, downloads in the background, installs on quit or on "Restart to update" |
| macOS | The app checks GitHub for the latest published release at start and every 24 hours. If it is newer, it shows "Version x is out" with a button that opens the website. It downloads and installs nothing |

LockedIn's screens show this themselves: a line on Today when an update is ready or out, and an "Updates" part of Me with the version, the state, "Check now" and the automatic switch. They use the `window.lh` bridge that exists. Wording in `policy.ts`. In development there is no updater.

User data lives outside the app and survives an update. Add a test that a data folder written by v3.2 opens in v4.0 (the weeks change in 5.1 is the one migration).

### 8.3 How Jiven ships an update

Rewrite `docs/desktop-release.md` as his runbook:

1. Merge the work to `main`. Change the version in `package.json` in its own PR.
2. Push the tag `v<version>`. Wait for the four builds and "Verify draft release".
3. Install the draft's build over the previous version on at least one Mac and one Windows machine: it opens, the data is still there, a Learn session starts.
4. Publish the draft. Windows and Linux copies pick it up within a day or at next start; Macs show the notice; the website rebuilds.
5. If the relay changed, it is deployed first and separately, with his yes, and must still serve the previous app version.

A bad release is withdrawn by publishing a higher version; an installed app never goes back by itself. Say so in the runbook.

### 8.4 The website

- `website/` in this repository: plain static files, no framework, in the Blocks look, drawing its colours from `src/core/companion/look.ts` the way `relay/scripts/look.ts` does for the phone.
- A workflow deploys it to GitHub Pages on a push that touches `website/` and when a release is **published**. At build time it reads the latest published release and writes the four download links and the version into the page, so the page needs no API call in the visitor's browser. With no release yet, the buttons say "Coming soon".
- Jiven turns Pages on once: repository Settings, Pages, Source "GitHub Actions".
- The page: what LockedIn is in two sentences; one download button chosen for the visitor's system with the other three beneath; how to install on each system, with the "Open Anyway" steps for Mac and the SmartScreen step for Windows, each with a picture; what it needs (a ChatGPT account to sign in with); what stays on the laptop and what leaves it (the relay: study blocks and phone answers; OpenAI: through the user's own sign-in; Deepgram: speech, only when Speak is used); the version and what changed; the source code and the licence (AGPL-3.0: offering the source is required); who made it.
- **The words on the page are Jiven's to approve (9.5).** Draft them, do not publish them unseen.
- Address: `https://jiven-chana.github.io/lockedin-companion/`. All links relative, so a domain can be added later.

## 11. Risks

- **Unsigned on macOS is the weakest point.** Every Mac user meets a security warning and updates by hand. If testers give up at "Open Anyway", decision 3 is the thing to revisit: an Apple membership (US$99 a year) removes both problems, and section 6.3 keeps that switch cheap.
- **No one has run this app packaged.** 6.1 exists to find out early. Expect it to find things.
- **An Intel Mac runner** may not be offered by GitHub for free much longer; if it goes, Intel Macs need a paid runner or are dropped.
- **Dictation cost** is bounded by caps on tokens, not on minutes. The account's own credit is the real limit.
- **The relay is one person's free account.** It has not been load-tested beyond the group.
- **The window bar on Windows and Linux** has never been seen with LockedIn's screens.
- **AGPL.** The app and the website must point to the exact source of the released version. The tag does that; keep the repository public.
